# PRD — 뉴스봇 (팀 프로젝트, 가제)

작성일: 2026-08-07
상태: Draft v0.1 (팀 프로젝트 주제 잠정 확정 — 팀원 배정·설계서 v1 공식 제출 전 초안)
범위: 카테고리 기반 뉴스 추출 + AI 요약 + TOP5 출력

> 라우팅 설계(도구 선택 + 개별 분기 처리) 상세와 작업 분할 전략은 [architecture.md](architecture.md) 참고.

## 1. 한 문장 정의

사용자가 관심 카테고리를 물으면, 오늘자 네이버 뉴스에서 해당 카테고리 기사를 모아 중복을 제거하고 AI로 요약한 TOP5 리스트를 보여주는 서비스다.

## 2. 배경

- LG CNS AI 캠퍼스 과정 2주차(8/10~8/14) 5일간 4인 팀으로 진행하는 팀 프로젝트. Day5(2026-08-07)에 잠정 주제로 확정했으며 변경 가능성이 있다.
- 팀장 개인 프로젝트 `discord-news-bot`(네이버 뉴스 검색 + OpenAI 요약, Node.js, 상시 운영 중)과 컨셉이 거의 동일해 설계 참고가 가능하다 — 단 실제 소스·프롬프트는 재사용하지 않고 이 과정에서 배우는 스택(LangChain/FastAPI/Pydantic)으로 새로 구현한다.
- 팀 결성 시점에 논의됐던 다른 후보("코드 리뷰 성장 코치")는 채택되지 않았다.

## 3. 문제와 목표

### 문제

- 관심 카테고리 뉴스를 매번 직접 검색·클릭해서 훑어봐야 해 시간이 든다.
- 같은 사건을 다루는 기사가 여러 매체에서 중복 노출돼 정보 밀도가 낮다.
- 헤드라인만으론 맥락 파악이 부족하지만, 기사 원문 전체를 읽기엔 부담스럽다.

### 목표

- 카테고리(또는 자연어 질문)를 입력하면 오늘자 관련 기사를 자동 수집한다.
- 중복 기사를 제거하고 상위 5건으로 압축한다.
- 각 기사를 AI가 짧게 요약해 제목·언론사·요약·원문링크 형태로 제공한다.

## 4. 사용자와 사용 맥락

| 사용자 | 맥락 | 필요 |
|---|---|---|
| 서비스 이용자 | 바쁜 아침/이동 중 특정 분야 뉴스를 빠르게 훑고 싶음 | 짧은 요약 + 원문 확인 가능한 링크 |
| 팀 프로젝트 발표 청중(강사·동료) | "이게 왜 흥미로운가"를 짧게 이해하고 싶음 | 명확한 스코프 + 실제 동작하는 데모 |

## 5. 핵심 가치

1. **정보 압축** — 여러 기사를 직접 읽지 않고도 오늘의 핵심을 파악한다.
2. **중복 제거** — 같은 사건을 다룬 여러 기사를 하나로 묶어 보여준다.
3. **원문 추적 가능** — 요약이 틀릴 수 있으므로 항상 원문 링크를 함께 제공한다.

## 6. 성공 지표

| 지표 | 목표(MVP 기준) |
|---|---|
| 카테고리 추출 성공률 | 테스트 질문 10개 중 8개 이상 올바른 카테고리 매핑 |
| 요약 구조화 성공률 | `with_structured_output` 파싱 실패율 5% 이하 |
| 중복 제거 정확도(주관 평가) | 팀 자체 검토로 같은 사건 기사 중복 노출 없는지 확인 |
| 응답 시간 | TOP5 요약까지 P50 5초 미만(비스트리밍 기준) |

## 7. MVP 범위 (MoSCoW)

**Must**
- 카테고리 추출(자연어 질문 → 카테고리) 또는 카테고리 직접 선택
- 네이버 뉴스 API로 오늘자 기사 조회
- 중복 기사 제거
- AI 요약(Pydantic 구조화 출력) → TOP5

**Should**
- SSE 스트리밍으로 요약 진행 상황(또는 기사별 요약) 실시간 표시
- LangSmith 트레이스 링크 제출

**Could**
- 여러 카테고리 동시 조회
- 요약 톤 조절(간단/상세)

**Won't (MVP 제외)**
- 사용자 장기 메모리(선호 카테고리 기억)
- 개인화 추천
- 복잡한 뉴스 랭킹(중요도 스코어링 등)
- 여러 날짜에 걸친 뉴스 분석/트렌드

## 8. 기능 요구사항

| ID | 요구사항 |
|---|---|
| FR-001 | 사용자 입력(자연어 질문 또는 카테고리 선택)을 받아 카테고리를 결정한다(구현: [architecture.md](architecture.md)) |
| FR-002 | 결정된 카테고리로 네이버 뉴스 API를 호출해 오늘자 기사 목록을 수집한다 |
| FR-003 | 제목/내용 유사도 기준으로 중복 기사를 제거한다 |
| FR-004 | 남은 기사 중 상위 5건을 선정해 각각 AI 요약을 생성한다 |
| FR-005 | 요약 결과는 Pydantic 스키마(`NewsItem`: title/press/summary/url, `NewsResponse`: category/items[])로 강제 구조화한다 |
| FR-006 | `GET /news/{category}`, `POST /news/search` 등 최소 2개 이상의 엔드포인트를 제공한다 |
| FR-007 | 엔드포인트 중 하나 이상은 SSE로 스트리밍 응답한다 |
| FR-008 | API 키(OpenAI, 네이버)는 `.env`로 관리하고 저장소에 커밋하지 않는다 |

## 9. 비기능 요구사항

- **응답 시간**: TOP5 요약까지 P50 5초 미만, P99 10초 미만(목표치, 실측 후 조정)
- **비용**: gpt-4o-mini 기준 요청당 비용을 tiktoken으로 실측해 이 섹션에 기재(아직 미측정)
- **재현 가능성**: 같은 카테고리·같은 날짜 재요청 시 유사한 결과가 나와야 한다(완전 결정론은 기대하지 않되 `temperature`는 낮게 유지)
- **비밀 정보 보호**: 네이버 API 키·OpenAI 키는 `.env`로만 관리, 저장소에 커밋 금지

## 12. 데이터 모델

아직 별도 ERD는 없음. 스코프 가드레일 원칙상 DB 연동 없이 무상태(in-memory) 처리가 기본 범위라, 영속화가 실제로 필요해지는 시점에 별도 ERD를 작성할 예정이다. 핵심 스키마는 8번 FR-005의 `NewsItem`/`NewsResponse` Pydantic 모델로 충분할 것으로 예상한다.

## 13. 제약과 정책

- DB 연동·사용자 인증·프론트엔드 UI·클라우드 배포는 이번 블록 범위 밖(스코프 가드레일) — 각각 in-memory, 인증 없음, 터미널/curl/`/docs`, 로컬 uvicorn으로 대체한다.
- 참고한 개인 프로젝트(`discord-news-bot`)의 실제 코드는 설계 참고만 하고 재사용하지 않는다 — 이 과정에서 배우는 스택으로 새로 구현한다.

## 14. 리스크와 완화책

| 리스크 | 완화책 |
|---|---|
| 네이버 뉴스 API 실시간 호출이 스코프 가드레일의 "실시간 외부 API는 Mock 권장" 원칙과 상충 | 핵심 기능이라 예외로 유지하되, API 장애 시 캐시된 샘플 데이터로 폴백하는 경로를 준비. 팀장이 강사에게 예외 인정 여부를 먼저 확인 |
| 중복 제거 기준이 애매(제목 유사도 vs 내용 유사도) | MVP는 제목 기준 단순 유사도로 시작하고, 필요시 임베딩 기반으로 심화 |
| 네이버 API 일일 호출 한도 초과 | 같은 카테고리 요청 결과를 짧게 캐싱(N분 재사용) |
| 5일이라는 짧은 기간에 4인 역할 배분이 불균형해질 위험 | 매일 오후 스탠드업에서 역할별 산출물 점검([architecture.md](architecture.md) 역할분담표 기준) |
| 카테고리별로 서비스 전체를 4벌 따로 만들어 "나중에 취합"하는 방식의 리스크 | 기각됨 — 대안은 [architecture.md](architecture.md) "작업 분할 전략" 참고 |

## 15. Open Questions
