# 발표 준비 — 뉴스봇 미니프로젝트 (가제)

관련 문서: [prd.md](prd.md), [architecture.md](architecture.md), [navigation.md](navigation.md)

> 아직 팀원 배정·실제 구현 전 초안. 8/14 발표 전까지 진행 내용에 맞춰 계속 갱신 필요.

## 1. 주제 선정 배경 (문제 상황 해결)

**문제 상황**
- 관심 카테고리 뉴스를 매번 직접 검색·클릭해서 훑어봐야 해 시간이 든다.
- 같은 사건을 다룬 기사가 여러 매체에서 중복 노출돼 정보 밀도가 낮다.
- 헤드라인만으론 맥락 파악이 부족하지만, 기사 원문 전체를 읽기엔 부담스럽다.

**왜 이 주제인가**
- 팀장 개인 프로젝트(`discord-news-bot` — 네이버 뉴스 검색+OpenAI 요약, 실제 운영 중)로 이미 실현 가능성이 검증된 컨셉 — 소스는 재사용하지 않고 이 과정 스택(LangChain/FastAPI/Pydantic)으로 새로 구현
- 도메인(뉴스)이 팀원 전원에게 익숙해 공감대 형성이 쉽고, 데이터 확보(네이버 뉴스 API)도 간단
- 필수요건 6종(FastAPI·프롬프트템플릿·Pydantic·SSE·LangSmith·`.env`)을 자연스럽게 채울 수 있는 스코프

**핵심 가치**
1. 정보 압축 — 여러 기사를 직접 읽지 않고도 오늘의 핵심 파악
2. 중복 제거 — 같은 사건을 다룬 기사를 하나로 묶어 제공
3. 원문 추적 가능 — 요약이 틀릴 수 있으므로 항상 원문 링크 동반

## 2. 프로젝트 설계 (6요소 기반)

| 요소 | 이 프로젝트 설계 |
|---|---|
| ① 프롬프트 전략 | RCIF 기반 카테고리별 요약 프롬프트, `ChatPromptTemplate` 변수로 구현(하드코딩 금지) |
| ② 체인 구조 | 메인 에이전트(`MainAgent`)가 사용자 질문을 보고 필요한 서브 에이전트를 도구로 선택 → `asyncio.gather`로 동시 호출 → 결과 종합 → 스트리밍 응답 |
| ③ 도구 목록 | 카테고리 3슬롯(경제 / 야구·건강 중 택1 / 개발)을 각각 `SubLLM` 서브클래스로 구현 — `MainLLM.create_tools()`가 이를 OpenAI 함수 호출 스키마로 변환해 LLM에 노출, 도구 선택 자체가 카테고리 라우팅 |
| ④ 상태 관리 | MVP는 무상태(세션 기억 없음, 스코프 제외) — Should로 "세션 내 최근 조회 카테고리 기억" 검토 |
| ⑤ 스트리밍 | `GET /news/{category}/stream`(SSE)으로 요약 진행 상황 실시간 표시(Should, 8/13 학습 후 구현) |
| ⑥ 비용·지연 | gpt-4o-mini 기준 tiktoken으로 요청당 비용 실측 예정. 목표 응답시간 P50 5초 미만, P99 10초 미만 |

데이터 흐름 다이어그램(mermaid)은 [architecture.md](architecture.md)에 있음 — 발표 3분 구간(데이터흐름+프롬프트전략)에 그대로 사용 가능.

### 왜 메인 에이전트와 서브 에이전트로 나눴는가

무작위 팀원 지목(8/14) 대비, 누가 질문받아도 바로 답할 수 있어야 하는 핵심 포인트. "하나의 큰 에이전트가 다 처리하면 안 되나?"라는 질문이 나올 걸 가정하고 아래 순서로 답한다.

1. **책임 분리** — 카테고리(경제/야구·건강/개발)마다 어떤 뉴스를 찾을지, 어떤 톤으로 요약할지가 다름. 서브 에이전트가 자기 카테고리 하나에만 집중하면 프롬프트와 로직이 단순해지고, 담당자가 서로의 코드를 안 건드리고 독립적으로 개발할 수 있음.
2. **동시성 = 응답 속도** — "경제랑 개발 뉴스 같이 보여줘"처럼 카테고리 두 개 이상 걸친 질문이 오면, 메인 에이전트가 필요한 서브 에이전트만 골라 `asyncio.gather`로 **동시에** 호출함. 순차 처리 대비 응답 시간이 줄어듦(카테고리 수만큼 곱해지지 않고, 가장 느린 서브 에이전트 하나만큼만 걸림).
3. **확장성** — 새 카테고리가 필요해지면 메인 에이전트 코드는 그대로 두고 `SubLLM` 서브클래스 하나만 추가하면 됨. `if/elif`로 한 함수 안에 다 넣는 방식이었다면 카테고리가 늘수록 그 함수가 계속 커졌을 것.
4. **라우팅을 LLM에게 위임** — 사용자가 카테고리를 직접 고르지 않아도, 메인 에이전트가 Function Calling으로 "이 질문엔 어떤 서브 에이전트가 필요한지" 스스로 판단. 자연어 질문 하나로 라우팅 + 실행 인자 추출이 동시에 됨.
5. **관심사 분리(사용자·히스토리는 메인만 관리)** — 사용자 식별(`user_id`)과 대화 히스토리(`self.memory`)는 메인 에이전트만 신경 쓰고, 서브 에이전트는 "이번 질문에 대한 답"만 만들면 됨. 서브 에이전트를 몇 개를 붙이든 이 책임 분리는 안 바뀜.

**설계 변경 히스토리(질문 나오면 이렇게 답변)**: 처음엔(8/7) 카테고리별로 서비스 전체를 따로 만드는 방식은 통합 리스크·중복 로직 때문에 기각하고 단일 에이전트 `if/elif` 분기로 시작했음. 이후(8/10) 공통 베이스 클래스(`Agent`/`SubLLM`/`MainLLM`)로 그 중복·통합 리스크를 상쇄할 수 있다고 판단해 멀티 에이전트로 전환함 — 즉 "처음부터 이렇게 설계했다"가 아니라 트레이드오프를 검토하고 방향을 바꾼 것. 근거는 [architecture.md](architecture.md) 상단 참고.

## 3. 진행 내용 (프롬프트 템플릿, 도구 구성 등)

**프롬프트 템플릿**
- `app/services/summarize.py` — RCIF(역할/맥락/지시/출력형식) 구조의 시스템 프롬프트, `with_structured_output`으로 `NewsItem`(title/press/summary/url)에 강제 구조화

**도구 구성**
- `app/llms/sub_agents.py` — 카테고리 3슬롯(경제/야구·건강 택1/개발)을 각각 `SubLLM` 서브클래스로 구현, `description`이 "언제 이 서브 에이전트를 쓰는지" 알려주는 라우팅 프롬프트 역할
- `MainLLM.create_tools()`로 서브 에이전트를 동시에 LLM에 노출 → 질문 하나로 카테고리 결정 + 실행 인자 추출을 한 번에 얻음 (왜 이렇게 나눴는지는 위 "왜 메인 에이전트와 서브 에이전트로 나눴는가" 참고)

**엔드포인트 (필수요건 6종 중 "2개 이상")**
- `GET /news/{category}` — 카테고리별 TOP5 요약
- `POST /news/search` — 자연어 질문 → 카테고리 라우팅 → 요약
- `GET /news/{category}/stream` — SSE 스트리밍(Should)

**현재까지 진행 상태**
- GitHub 레포(`jh3779/LG-CNS-AICAMPUS`) 생성 완료, 설계 문서(PRD·아키텍처·네비게이션) + FastAPI 뼈대(빈 파일, 폴더 구조만) 커밋·푸시 완료
- 실제 구현은 2주차(8/10~) 로드맵에 맞춰 진행 예정: 8/10 비동기 → 8/11 FastAPI → 8/12 Pydantic 검증 → 8/13 SSE → 8/14 스프린트+발표

## 4. 구현 방식 (소통 방법, 역할 분담)

**소통 방법**
- GitHub 레포 공유(문서·코드 단일 소스) — PRD/아키텍처 문서로 설계 합의를 먼저 기록하고 코드는 그 위에 얹음
- 빅뱅 통합 금지 — 매일 오후 스탠드업에서 조금씩 취합(팀 채널은 팀 결성 후 확정)

**역할 분담 (가제)**

| 역할 | 담당 | 비고 |
|---|---|---|
| 팀장 | 카테고리 범위 결정·일정 조율·발표 총괄 | |
| 메인 에이전트 담당 | `Agent`/`SubLLM`/`MainLLM` 베이스 클래스, `MainAgent` 오케스트레이터(동시 호출·히스토리·스트리밍) | |
| 서브 에이전트 담당(3명) | `BusinessAgent`(경제), `BaseballAgent`/`HealthAgent`(야구·건강 택1), `DevelopmentAgent`(개발) 각 1개씩 | **담당 카테고리는 배정이 아니라 자율 선택** |
| 테스트·QA·발표 | 엣지케이스(기사 0건·중복 과다·모호한 카테고리) 테스트, 데모·발표 준비 | |

**작업 순서**: 공통 베이스 클래스(`app/llms/agent.py`)를 먼저 두고 → 그 위에서 메인 에이전트와 서브 에이전트 3개를 담당자별로 병렬로 채우는 방식. 카테고리별 서비스를 완전히 따로 만드는 방식은 8/7엔 통합 리스크·중복 로직 문제로 기각했었지만, 8/10에 공통 베이스 클래스로 그 리스크를 상쇄할 수 있다고 판단해 멀티 에이전트로 전환함(근거: [architecture.md](architecture.md) "작업 분할 전략").
