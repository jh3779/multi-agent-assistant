## 1. 주제 선정 배경 (문제 상황 해결)

**문제 상황**
- 관심 카테고리 뉴스를 매번 직접 검색·클릭해서 훑어봐야 해 시간이 든다.
- 같은 사건을 다룬 기사가 여러 매체에서 중복 노출돼 정보 밀도가 낮다.
- 헤드라인만으론 맥락 파악이 부족하지만, 기사 원문 전체를 읽기엔 부담스럽다.

**왜 이 주제인가**
- 팀장 개인 프로젝트(`discord-news-bot` — 네이버 뉴스 검색+OpenAI 요약, 실제 운영 중)로 이미 실현 가능성이 검증된 컨셉 — 소스는 재사용하지 않고 이 과정 스택(LangChain/FastAPI/Pydantic)으로 새로 구현
- 도메인(뉴스)이 팀원 전원에게 익숙해 공감대 형성이 쉽고, 데이터 확보(네이버 뉴스 API)도 간단
- 필수요건 6종(FastAPI·프롬프트템플릿·Pydantic·SSE·LangSmith·`.env`)을 자연스럽게 채울 수 있는 스코프

**핵심 가치**
1. 정보 압축 — 여러 기사를 직접 읽지 않고도 오늘의 핵심 파악
2. 중복 제거 — 같은 사건을 다룬 기사를 하나로 묶어 제공
3. 원문 추적 가능 — 요약이 틀릴 수 있으므로 항상 원문 링크 동반

## 2. 프로젝트 설계 (6요소 기반)

| 요소 | 이 프로젝트 설계 |
|---|---|
| ① 프롬프트 전략 | RCIF 기반 카테고리별 요약 프롬프트, `ChatPromptTemplate` 변수로 구현(하드코딩 금지) |
| ② 체인 구조 | LCEL: 도구 선택(라우팅) → `if` 분기(개별 처리) → 네이버 API 호출 → 중복 제거 → 요약 → 구조화 출력 |
| ③ 도구 목록 | 카테고리 4종을 `@tool`로 등록(정치/경제/IT/스포츠, "기타" 없음) — `bind_tools`로 LLM에 노출, 도구 선택 자체가 카테고리 라우팅 |
| ④ 상태 관리 | MVP는 무상태(세션 기억 없음, 스코프 제외) — Should로 "세션 내 최근 조회 카테고리 기억" 검토 |
| ⑤ 스트리밍 | `GET /news/{category}/stream`(SSE)으로 요약 진행 상황 실시간 표시(Should, 8/13 학습 후 구현) |
| ⑥ 비용·지연 | gpt-4o-mini 기준 tiktoken으로 요청당 비용 실측 예정. 목표 응답시간 P50 5초 미만, P99 10초 미만 |

데이터 흐름 다이어그램(mermaid)은 [architecture.md](architecture.md)에 있음 — 발표 3분 구간(데이터흐름+프롬프트전략)에 그대로 사용 가능.

## 3. 진행 내용 (프롬프트 템플릿, 도구 구성 등)

**프롬프트 템플릿**
- `app/services/summarize.py` — RCIF(역할/맥락/지시/출력형식) 구조의 시스템 프롬프트, `with_structured_output`으로 `NewsItem`(title/press/summary/url)에 강제 구조화

**도구 구성**
- `app/tools/category_tools.py` — 카테고리 4개를 각각 `@tool`로 등록, docstring이 "언제 이 도구를 쓰는지" 알려주는 라우팅 프롬프트 역할
- `bind_tools`로 4개 도구를 동시에 LLM에 노출 → 질문 하나로 카테고리 결정 + 검색어 추출을 한 번에 얻음

**엔드포인트 (필수요건 6종 중 "2개 이상")**
- `GET /news/{category}` — 카테고리별 TOP5 요약
- `POST /news/search` — 자연어 질문 → 카테고리 라우팅 → 요약
- `GET /news/{category}/stream` — SSE 스트리밍(Should)

**현재까지 진행 상태**
- GitHub 레포(`jh3779/LG-CNS-AICAMPUS`) 생성 완료, 설계 문서(PRD·아키텍처·네비게이션) + FastAPI 뼈대(빈 파일, 폴더 구조만) 커밋·푸시 완료
- 실제 구현은 2주차(8/10~) 로드맵에 맞춰 진행 예정: 8/10 비동기 → 8/11 FastAPI → 8/12 Pydantic 검증 → 8/13 SSE → 8/14 스프린트+발표

## 4. 구현 방식 (소통 방법, 역할 분담)

**소통 방법**
- GitHub 레포 공유(문서·코드 단일 소스) — PRD/아키텍처 문서로 설계 합의를 먼저 기록하고 코드는 그 위에 얹음
- 빅뱅 통합 금지 — 매일 오후 스탠드업에서 조금씩 취합(팀 채널은 팀 결성 후 확정)

**역할 분담 (가제)**

| 역할 | 담당 | 비고 |
|---|---|---|
| 팀장 | 카테고리 범위 결정·일정 조율·발표 총괄 | |
| 구현 리드 | 네이버 API 연동, 체인 구조, 엔드포인트 배선, 공통 스켈레톤 선구축(8/10~11) | |
| 프롬프트·기획 | 카테고리 추출·요약 프롬프트(RCIF), Pydantic 스키마 설계 | |
| 테스트·QA·발표 | 엣지케이스(기사 0건·중복 과다·모호한 카테고리) 테스트, 데모·발표 준비 | |
| 팀원 4명 공통 | `handle_정치`/`handle_경제`/`handle_it`/`handle_스포츠` 각 1개씩 개별 구현 | **담당 카테고리는 배정이 아니라 자율 선택** |

**작업 순서**: 구현 리드가 공통 스켈레톤을 먼저 만들고(도구 등록/분기 껍데기, 중복제거, 요약, FastAPI 라우팅, Pydantic 스키마) → 그 위에서 4명이 카테고리별 `handle_*()` 본문을 병렬로 채우는 방식. 카테고리별로 서비스 전체를 따로 만들어 나중에 합치는 방식은 통합 리스크·중복 로직 문제로 기각함(근거: [architecture.md](architecture.md) "작업 분할 전략").
