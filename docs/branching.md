# 브랜치 규칙

`main`은 보호 브랜치로 설정되어 있음. 아래 규칙은 4인 팀 + AI(Claude Code 등) 협업을 전제로 한 최소한의 규칙.

## main 브랜치 보호 설정

GitHub에 실제로 걸려 있는 규칙(2026-11-26 확인):

- **CI `test` 통과 필수** — 병합 전에 브랜치가 `main`의 최신 상태여야 함(strict)
- **관리자에게도 적용**
- **force-push 금지**
- **브랜치 삭제 금지**

리뷰 승인은 GitHub 설정으로 강제하지 않는다. 아래 "작업 흐름"의 리뷰 요청과 "AI 협업 시"의 리뷰 원칙은 **팀 합의(관례)**이며 시스템이 막아주지 않으므로, PR 작성자가 직접 지켜야 한다.

## 브랜치 네이밍

```
feature/<짧은-설명>   # 새 기능 (예: feature/kbo-agent)
fix/<짧은-설명>       # 버그 수정
docs/<짧은-설명>      # 문서 작업
chore/<짧은-설명>     # 설정, 의존성 등 기타 작업
```

## 작업 흐름

1. `main`에서 새 브랜치 생성
2. 작업 진행 (AI 도구 사용 여부 무관, 아래 "AI 협업 시" 참고)
3. 커밋 후 push, PR 생성
4. 팀원 1명 이상에게 리뷰 요청
5. 승인 후에만 병합 (Squash merge 권장, 커밋 히스토리 깔끔하게 유지)

## AI 협업 시

Claude Code 등 AI 에이전트로 브랜치 작업이나 커밋을 진행하는 경우에도 위 규칙이 동일하게 적용됨. AI가 생성한 코드도 예외 없이 사람 리뷰를 거쳐야 `main`에 들어감.

- PR 설명에 AI가 생성/보조한 부분이 있으면 간단히 표시 (예: "AI로 초안 작성, 로직 직접 검증함")
- 리뷰어는 AI 생성 코드라고 그냥 승인하지 말고, 직접 작성한 코드와 동일한 기준으로 검토
